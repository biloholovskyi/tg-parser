# ADR — кэш каналов в Redis

## Статус

Принято, выбрано пользователем 14.10.2026; реализовано в 1.6.0 (вопрос «Что делать при лимите Telegram»).

## Контекст

Каждый запуск дайджеста ищет все каналы по имени через `contacts.ResolveUsername`, у которого суточный лимит на аккаунт. 12.10.2026 лимит сорвал дайджест. Клиент между запусками выселяется, `StringSession` сущности не хранит.

## Решение

- Хранить `channelId` и `accessHash` канала в Redis под ключом `tg:peer:{sha256(sessionString)}:{username}` со сроком `CHANNEL_PEER_TTL_S`, продлеваемым при использовании.
- Значения хранятся без шифрования: это не учётные данные, без авторизованной сессии они бесполезны. Ключ содержит только SHA-256 сессии.
- Без Redis — ограниченный кэш в памяти процесса.
- Устаревшая запись удаляется по ошибке Telegram, после чего канал ищется по имени один раз.

## Отвергнуто

- Шифровать значения `SESSION_ENCRYPTION_KEY`: защищает данные, которые не являются секретом, и связывает кэш с ключом шифрования.
- Держать клиента дайджеста подключённым весь день: постоянные пинги Telegram и нарушение правила выселения простаивающих клиентов.
- Хранить кэш на диске: файловая система деплоя эфемерна.

## Последствия

- Поиск по имени выполняется один раз на канал в `CHANNEL_PEER_TTL_S`, а не каждый вечер.
- Если имя канала тихо перешло к другому каналу, старый канал читается до истечения записи или до ручного удаления ключей.
- Обновляются правила `architecture.md`, `telegram.md`, `runtime-resources.md` и `CLAUDE.md`: в Redis появляется второй тип записей.
