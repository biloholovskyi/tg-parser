# Блоки 03-05 — Reflect

Итоговое размышление по плану после Finalize (2026-09-23, версия 1.4.1, ветка `r-1.4.1`).

## Соответствие миссии

- Потолок, срок жизни и путь освобождения клиента: выполнено. `SessionClientCache` ограничен SESSION_CACHE_MAX_ENTRIES, простаивающие записи собираются по SESSION_CACHE_IDLE_TTL_MS, каждое вытеснение вызывает `destroy`. Отозванная сессия теперь удаляется и из файлового хранилища, чтобы не восстанавливаться и не переподключаться на каждом вызове. Не подтверждено живым прогоном: что число живых клиентов остаётся ровным после нескольких реальных сессий.
- Честный ответ: выполнено в коде и тестах. Выборка несёт `isTruncated`, отказ Telegram отражается кодом состояния через `toHttpException`. На реальном загруженном канале `isTruncated=true` не проверялся.
- Чистые логи: выполнено. Весь вывод через `Logger`, `console.*` запрещён линтером и тестом, одна строка исхода на запрос, логгер GramJS на уровне ERROR. Дымовой прогон на подставных данных показал ноль вхождений подставного номера, сессии и кода.

## Соответствие замыслу

- Границы плана соблюдены: `src/main.ts` и периметр контроллера не менялись по существу (в контроллере изменён только комментарий к `/me` под новые коды), файловое хранилище не расширялось.
- Одно отступление от буквы границы: при отзыве сессии запись удаляется из файлового хранилища. Это не расширение хранилища, а освобождение ресурса, которое требует `runtime-resources.md`; судьба самого хранилища по-прежнему за блоком 08-09.
- Критерий приёмки Phase 04 «число живых клиентов не растёт после нескольких сессий» формально не закрыт: для него нужен реальный аккаунт Telegram. Закрыт только тестами жизненного цикла кэша.

## Уроки

- Сопоставление ошибок по подстроке сообщения опасно: GramJS включает в текст ошибки вводимые пользователем данные (имя канала), и такое имя могло подделать 401, 429 или 503. Классифицировать ошибки MTProto надо только по точному коду. Это нашёл аудит безопасности, а не тесты фаз — тесты проверяли правильные ошибки, а не враждебный ввод.
- `disconnect` в GramJS не останавливает цикл обновлений, освобождает клиента только `destroy`. Без проверки поведения библиотеки «вытеснение с отключением» оставило бы утечку невидимой.
- Логгер GramJS по умолчанию пишет сам, в обход `Logger`; запрета `console.*` в `src/` для чистых логов недостаточно, нужны явные опции библиотеки.
- Неизвестная и отозванная сессии должны давать один и тот же 401, иначе ответ раскрывает, какие сессии сервис знает.
- Аудиты после последней рабочей фазы нашли несколько дефектов в коде самого блока (M1, M2, M-1, M-2, M-3). Выносить аудит ресурсов и безопасности только в Finalize для плана такого риска поздно — стоит запускать его после фазы жизненного цикла.

## Технический долг

- Файловое хранилище сессий пишет номера и строки сессий в `data/` (Known Deviation, security C1, resource H-2) — блок 08-09.
- Карта состояний авторизации имеет TTL, но не имеет потолка размера (security H-1).
- 429, порождённый сервисом, не ставит заголовок `Retry-After`; ожидание только в теле (`retryAfterSeconds`).
- Нет общего срока на запрос выборки постов: обход может занять до ~13 × EXTERNAL_CALL_TIMEOUT_MS (resource M-4).
- Обработчик `uncaughtException` завершает процесс (resource M-5, существовало до плана).
- Неверный код или пароль уничтожает ожидающую авторизацию (security M3).
- Проверка конфигурации есть только на пути авторизации: без учётных данных пути сессий отвечают 502/503 вместо 500 (security L4).
- `authenticate()` далеко за пределом длины функции (security L5) — распил в блоке 08-09.
- LRU может вытеснить клиента посреди обхода выборки (resource L-2).
- Двойное освобождение при сбое подключения на шаге 1 авторизации (resource L-3, безвредно).
- На момент фазы 02 не были покрыты тестами (`history.md`; после Finalize не перепроверялось): медиа-ветки `parseMessage`, восстановление из `data/*.json`, ответ `needsPassword`.
