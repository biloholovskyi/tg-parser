# ADR — Хранилище сессий

Дата: 24.09.2026

Статус: принято пользователем

## Контекст

`TelegramService` сохранял строки сессий в `data/sessions.json`, а номера телефонов с хешами кодов — в `data/auth-states.json`. Это противоречило модели «только память» и правилу о секретах в `.claude/rules/telegram.md`. Файловая система Railway эфемерна: содержимое `data/` исчезает при каждом выкате, поэтому файлы не давали пережить деплой, но держали учётные данные на диске и выполняли синхронный ввод-вывод на пути запроса.

## Варианты

- Только память — секреты не покидают процесс; после перезапуска строку сессии нужно получить заново.
- Внешнее хранилище с шифрованием — сессии переживают перезапуск; цена: новая зависимость, управление ключом, расходы.
- Оставить файлы — без изменений кода; учётные данные на диске без пользы.

## Решение

Только память. Файловое хранилище удалено: сессии живут в `SessionStore` (ограниченный кэш клиентов в памяти процесса), незавершённые попытки входа — в `AuthService`. Каталог `data/` не создаётся, ни один файл не читается и не пишется.

## Последствия

- Перезапуск или выкат сбрасывает все сессии: вызывающий получает 401 на маршруте постов и `failed` на `/telegram/me` и проходит авторизацию заново. Фактически так было и раньше из-за эфемерного диска.
- Незавершённая авторизация не переживает перезапуск: шаг с кодом после рестарта отвечает 400, код нужно запросить снова.
- Горизонтальное масштабирование по-прежнему требует отдельного решения.
- Если понадобится переживать перезапуск, внешнее шифрованное хранилище оформляется отдельным планом.
