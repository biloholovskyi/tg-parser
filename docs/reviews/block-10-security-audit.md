## Проверено и чисто

- Периметр. `PUT /digest/session` и `POST /digest/run` закрыты `x-api-key` и лимитом RATE_LIMIT_DEFAULT: гарды `ApiKeyGuard`, `RateLimitGuard`, `PhoneRateLimitGuard` зарегистрированы как `APP_GUARD` в `src/telegram/telegram.module.ts:26-28` и действуют на всё приложение, включая `DigestController`. `@PublicRoute()` на новых маршрутах нет.
- Передача учётных данных. Строка сессии для `PUT /digest/session` приходит только в заголовке `x-session-string` (`src/digest/digest.controller.ts:33`, `src/shared/utils/session-header.ts:11-15`); в пути и query её нет. Повторённый заголовок считается отсутствующим.
- Строка сессии не попадает в логи, тексты ошибок и ключи Redis. Ключ записи — SHA-256 (`src/telegram/session-repository.ts:124-126`), значение зашифровано; отметка дайджеста хранит хеш, а не строку (`session-repository.ts:83`). Единственная строка лога при сбое записи использует `describeError` от уже обёрнутого 503 (`src/telegram/session-store.ts:66`).
- `REDIS_URL` не логируется: `src/redis/redis-client.ts:43` пишет только `error.code`/`error.name`, один раз на обрыв. Ошибка Redis остаётся в `cause` исключения 503 (`session-repository.ts:115-121`), а стандартный фильтр Nest `cause` в ответ не отдаёт.
- Ключ Grok уходит только в заголовке `Authorization` (`src/digest/grok/grok.client.ts:64`); ошибки Grok несут только статус или причину, без тела запроса и ответа (`grok.client.ts:93-131`). Токен бота есть только в URL исходящего запроса (`src/digest/bot-notifier.ts:66`); URL не логируется, у сетевых ошибок берётся только `error.name` (`bot-notifier.ts:106-114`).
- Все новые секреты читаются только загрузчиками `src/config/` (`redis.config.ts:23-24`, `digest.config.ts:60-62`); `process.env` вне `src/config/` и `src/main.ts` нет. Предупреждения называют переменные, но не значения.
- AES-256-GCM (`src/shared/utils/secret-cipher.ts`): случайный IV на каждую запись, 12 байт; тег 16 байт, вырезается фиксированной длиной, так что атака укороченным тегом невозможна; длина ключа 32 байта проверяется в `redis.config.ts:30-31`, а неверный ключ переводит сервис в режим «только память», а не в хранение без шифрования. Запись, которая не расшифровывается, удаляется и считается неизвестной (`session-repository.ts:106-111`).
- Ответы не раскрывают, существует ли сессия. Неизвестная и отозванная сессии дают один и тот же 401 (`telegram-errors.ts:150-152`); восстановление требует записи в хранилище (`session-store.ts:112-115`), поэтому через сервис нельзя подключить чужую строку сессии, которую сервис не выдавал. Недоступный Redis даёт одинаковый 503 для любой сессии.
- Тексты постов, в том числе из приватных каналов, не логируются: `PostCollector`, `TranslationService`, `SummaryService`, `DigestService` пишут только счётчики.
- Экранирование HTML для бота. Тезисы, точки зрения, имена каналов и причины сбоя проходят через `escapeHtml` (`src/digest/utils/digest-formatter.ts:25,43,45,100`). В `href` попадает только URL, собранный сервисом из проверенного по шаблону имени канала и числового id (`src/telegram/utils/message.mapper.ts:13`), и он дополнительно экранирован вместе с `"` (`src/digest/utils/html.ts:10`). Модель не может подставить ссылку: ссылки строятся по `ref`, а неизвестные `ref` отбрасываются (`src/digest/utils/coverage.ts:7-17`). Внедрить `href` через ответ модели нельзя.
- Имена каналов из `DIGEST_CHANNELS` проверяются тем же шаблоном, что и параметр маршрута (`digest.config.ts:70-76`), и ограничены DIGEST_MAX_CHANNELS.
- GramJS не импортируется вне `src/telegram/`; `DigestModule` работает только через фасад `TelegramService`.
- Нет `any`, `console.*`, `eval`, `new Function` в изменённых файлах вне тестов.
- В новых и изменённых файлах (включая `docs/testing/digest-*`) нет настоящих учётных данных: только очевидные подделки (`fake-password`, номера `+1000000000x`, `fake-session-string`).
- Новые зависимости: у `ioredis@6.0.0` и `cron@3.2.1` известных уязвимостей нет.

## MEDIUM

### M1 (новый) — `POST /digest/run` без собственного интервала: держатель ключа запускает дайджест подряд

- Файл: `src/digest/digest.controller.ts:20-24`, `src/digest/digest.service.ts:59-68`.
- Что происходит: одновременно идёт только один прогон, но сразу после окончания следующий запрос с тем же ключом запускает новый. Лимит RATE_LIMIT_DEFAULT (60 в минуту) тут ничего не ограничивает: прогон длится минуты. Каждый прогон — до DIGEST_MAX_CHANNELS чтений каналов от имени аккаунта Telegram, десятки платных запросов к Grok и сообщения в чат.
- Атака: утёкший или неосторожно используемый ключ API превращает сервис в непрерывный цикл чтения каналов. Это тратит деньги на Grok и приближает аккаунт к flood wait (временному запрету Telegram на частые запросы) или к блокировке. `risks.md` признаёт риск, но мера «расход ограничен длительностью прогона» ограничивает параллельность, а не частоту.
- Исправление: минимальный интервал между ручными запусками (константа, например `DIGEST_MANUAL_COOLDOWN_MS`, отсчёт от конца прошлого прогона, ответ 429 с `Retry-After`), либо отдельный лимит на маршрут в несколько запусков в сутки. Тест: второй запуск внутри интервала получает 429.

### M2 (новый) — глобальную отметку дайджеста может переписать любой держатель ключа

- Файл: `src/digest/digest.controller.ts:31-38`, `src/telegram/telegram.service.ts:84-91`, `src/telegram/session-repository.ts:77-84`.
- Что происходит: сессия дайджеста одна на весь сервис, а `PUT /digest/session` доступен любому ключу из `API_KEYS`. Привязки к владельцу нет, и ключи API никак не различаются по правам.
- Атака: второй держатель ключа отмечает свою сессию, затем завершает её в Telegram. Дайджест владельца перестаёт работать (401 при каждом запуске), и чтение идёт уже не тем аккаунтом, который выбирал владелец. При одном ключе риск нулевой, при нескольких это отказ в обслуживании и подмена источника чтения.
- Исправление: отдельный ключ администратора для маршрутов `/digest/*` (например, переменная `DIGEST_ADMIN_API_KEYS`, читается загрузчиком в `src/config/`) или запись в лог, чья отметка действует (без самого ключа, по его хешу). Как минимум — записать в ADR, что все держатели ключей считаются одним доверенным владельцем.

### M3 (новый) — внедрение команд в запрос к Grok через текст постов: подмена переводов и фишинговые ссылки в чате владельца

- Файл: `src/digest/translation.service.ts:67-80`, `src/digest/summary.service.ts:54-63`, `src/digest/grok/schemas.ts`, `src/digest/utils/digest-formatter.ts:42-51`.
- Что происходит: текст постов идёт в Grok как данные внутри того же сообщения, что и инструкции. Проверка `ref` не даёт модели выдумать ссылки, но содержание не проверяется. Внутри одной партии перевода принимается перевод для любого `ref` из партии (`translation.service.ts:74-78`), а поле `source` в точке зрения — свободный текст.
- Атака: автор одного канала из списка публикует пост с инструкцией для модели. Модель (а) переписывает переводы постов других каналов той же партии; (б) приписывает утверждение чужому каналу через `source`; (в) вставляет в тезис текст с адресом. Экранирование HTML защищает разметку, но Bot API сам делает кликабельными адреса и `@упоминания` в обычном тексте, поэтому фишинговая ссылка («войдите в Telegram, чтобы…») будет рабочей. Это прямой путь к владельцу аккаунта, чья сессия лежит в сервисе. Утечки секретов нет: у модели нет инструментов, а в запросе нет ни ключей, ни строк сессий.
- Исправление: (1) в `escapeHtml`-вывод добавить обезвреживание адресов и упоминаний в тексте модели (например, вставлять невидимый разделитель после `://`, `t.me/` и `@` или оборачивать тезисы в `<code>`/`<blockquote>`, где автоссылки не создаются), так чтобы кликабельными оставались только ссылки, построенные сервисом; (2) переводить посты разных каналов в разных партиях или по одному каналу за запрос, чтобы пост не мог переписать чужой перевод; (3) принимать `source` только из множества имён каналов прогона; (4) в системном промпте прямо сказать, что текст постов — данные, а не инструкции. Пункт 4 без 1–3 не защищает.

### M4 (новый) — инструкция по Railway оставляет Redis доступным из интернета

- Файл: `docs/deployment/railway-redis.md:164`, в связке со строкой 65.
- Что происходит: строка 65 справедливо предупреждает о `REDIS_PUBLIC_URL`, а строка 164 советует им пользоваться для `FLUSHDB`. Шаблон Redis на Railway создаёт публичный TCP-прокси (сетевой проход из интернета к базе), и инструкция нигде не говорит его отключить.
- Атака: Redis с паролем открыт из интернета. Строки сессий зашифрованы, поэтому чтение базы аккаунты не раскрывает, но подбор пароля или его утечка дают `FLUSHALL` (все вызывающие теряют сессии) и перезапись `tg:digest-session` на хеш другой сохранённой сессии — дайджест начнёт читать каналы чужим аккаунтом из числа выданных сервисом.
- Исправление: в шаг 1 добавить «Settings → Networking → удалить TCP Proxy у сервиса Redis»; в разделе про смену ключа чистить базу через вкладку "Data" или `railway connect` / временный прокси, который удаляется сразу после работы.

### M5 (перенесён из M2 блока 08-09, усилен Redis) — нет пути отзыва сессии, а записи живут 30 дней

- Файл: `src/telegram/constants.ts:98` (SESSION_STORE_TTL_S), `src/telegram/session-store.ts:88-99`, `src/telegram/session-repository.ts:58-74`.
- Что происходит: запись удаляется из Redis только когда Telegram сам отверг сессию. Вытеснение из кэша (`evict`) запись не трогает, и в сервисе нет ни маршрута выхода, ни вызова `auth.LogOut`. Раньше перезапуск хотя бы обрывал доступ через сервис; теперь любая выданная сессия (не только сессия дайджеста) восстанавливается автоматически 30 дней с последнего использования.
- Атака: утёкшая строка сессии плюс любой ключ API дают доступ к аккаунту через сервис в течение всего TTL, и у вызывающего нет способа закрыть её со стороны сервиса. В самом Telegram авторизация остаётся живой в любом случае.
- Исправление: маршрут `DELETE /telegram/session` (сессия в заголовке, ключ API, лимит), который вызывает `auth.LogOut`, `evict` и `repository.remove`; сохранять в Redis только сессии, которые об этом явно попросили (например, отмеченная для дайджеста), или сократить SESSION_STORE_TTL_S для остальных. Решение о том, какие сессии хранить, — пользовательское, по ADR; здесь фиксируется только отсутствие отзыва.

## LOW

### L1 — шифротекст не привязан к ключу записи

`src/shared/utils/secret-cipher.ts:15-20,23-34`. Без AAD (дополнительных данных, которые шифр проверяет вместе с тегом) запись можно переложить под другой ключ Redis. Для `isKnown` это безвредно, потому что расшифрованная строка сравнивается с предъявленной (`session-repository.ts:43`), но `loadDigest` такой проверки не делает. Исправление: передавать хеш записи как AAD (`cipher.setAAD`) при шифровании и расшифровке.

### L2 — ключ шифрования проверяется только по длине

`src/config/redis.config.ts:30-31`. `Buffer.from(..., 'base64')` молча пропускает недопустимые символы, поэтому 43–44-символьная парольная фраза может дать 32 байта с низкой энтропией, а ключ из одних нулей тоже проходит. Исправление: требовать строгий base64 (проверка шаблоном и совпадение при обратном кодировании) и отвергать ключ из одинаковых байтов.

### L3 — хеш записи без секрета

`src/shared/utils/secret-cipher.ts:37-39`. Обычный SHA-256 от строки сессии. Подобрать высокоэнтропийную строку сессии нельзя, но держатель базы может проверить, хранится ли известная ему строка. Исправление: HMAC-SHA-256 с отдельным ключом, производным от SESSION_ENCRYPTION_KEY.

### L4 — ключ шифрования и адрес Redis лежат в одном месте

`docs/plans/block-10-daily-digest/adr-session-redis.md` (последствия), `docs/deployment/railway-redis.md:9`. Шифрование защищает от утечки одной базы или её резервной копии, но не от доступа к переменным сервиса на Railway: там есть и `REDIS_URL`, и ключ. ADR это признаёт; стоит явно записать, что круг людей с доступом к переменным Railway равен кругу людей с доступом ко всем аккаунтам.

### L5 — ключ в истории оболочки

`docs/deployment/railway-redis.md:111`. `railway variables --set "SESSION_ENCRYPTION_KEY=..."` оставляет ключ в истории PowerShell/bash. Исправление: рекомендовать ввод через Dashboard или чтение из буфера/переменной без записи в историю.

### L6 — Redis без TLS и с полными правами

`src/redis/redis-client.ts:25-32`, `docs/deployment/railway-redis.md:25`. Соединение `redis://` в частной сети Railway, пользователь `default` с правом на `FLUSHALL`/`CONFIG`. Исправление: при появлении публичного доступа — только `rediss://`; отдельный пользователь ACL с доступом к префиксу `tg:*` и без опасных команд.

### L7 — текст приватных каналов уходит к стороннему провайдеру

`src/digest/grok/grok.client.ts:57-75`. Осознанное решение пользователя (`risks.md`, раздел «Экспозиция секретов»), повторно не оспаривается. Рекомендация: проверить настройки хранения данных у xAI для этого ключа API и записать выбранный режим в ADR.

### L8 — Postman сохраняет настоящую строку сессии в переменную коллекции

`docs/testing/digest-postman-collection.json:62`. `pm.collectionVariables.set('sessionString', …)` записывает строку в коллекцию; при повторном экспорте и коммите реальная сессия попадёт в репозиторий. Исправление: `pm.environment.set` в локальном окружении, которое не коммитится, или `pm.variables` (только на время запуска).

### L9 — документы расходятся с моделью хранения

`CLAUDE.md:5` («Nothing is written to disk») и `.claude/rules/api-security.md:44` («never written to disk») против `docs/deployment/railway-redis.md:39-49`, где Redis с `--appendonly yes` пишет зашифрованные строки сессий на том Railway. Исправление: уточнить формулировку — «в открытом виде на диск не пишется; зашифрованные записи хранятся в Redis».

## Вердикт

Блок 10 не вносит уязвимостей уровня CRITICAL или HIGH. Строки сессий, ключ шифрования, ключ Grok, токен бота и `REDIS_URL` не попадают ни в логи, ни в ответы, ни в URL, ни в ключи Redis. AES-GCM применён правильно, новые маршруты закрыты ключом и лимитом. В текущем виде сервис можно держать открытым только при условии, что все держатели `API_KEYS` доверенные (M1, M2, M5). Если Redis остаётся доступным из интернета (M4) и в списке `DIGEST_CHANNELS` есть каналы, авторам которых нельзя доверять (M3), M3 и M4 нужно закрыть до постоянной работы дайджеста.
